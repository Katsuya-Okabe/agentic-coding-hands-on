## ハンズオン（午前）：Vibe Coding の限界を体験する

### 1. Vibe Chat に機能追加を依頼する

昨日と同じ Vibe Coding のルール（コードは読まない、提案はそのまま承認）で進めます。

1.  Claude Code のチャットパネルで、[hands-on/day2/change-request.prompt.txt](../hands-on/day2/change-request.prompt.txt) を貼り付けて送信します。
2.  完成したら起動し、**追加した機能**と**昨日まで動いていた機能**の両方をブラウザで確認します。
3.  動かないところがあれば、昨日と同じようにエラーを貼り付けて直させます。

> [!NOTE]
> 制限時間は60分です。終わらなくても構いません。「終わらなかった」ことも大切な記録です。

記録すること（比較シートの「Vibe Chat（Day2 変更）」欄）：

*   直させた回数（手戻り回数）
*   一度直ったのに、また壊れた機能（デグレ）の数
*   60分で終わったかどうか

### 2. 品質を検証する

ここからは **AI に頼らず、自分で** 調べます。[hands-on/day2/inspection-commands.md](../hands-on/day2/inspection-commands.md) のコマンドを順に実行し、結果を比較シートに記入します。

*   テストはあるか
*   Lint / Format は設定されているか
*   脆弱性のある依存パッケージはないか
*   古いライブラリを使っていないか
*   AI が説明なしに追加したライブラリはいくつあるか
*   既存機能は壊れていないか

### 3. 問題点を4つに分類する（チーム）

チームで見つけた問題を付箋（またはホワイトボード）に書き出し、書籍 4.2 の4分類に当てはめます。

| 分類 | 例 | 自分たちが見つけた問題 |
| :--- | :--- | :--- |
| 曖昧な要件による破綻 | 「イケてる感じ」が人によって違う | |
| 存在しない検証条件 | テストがなく、壊れたことに気づけない | |
| スタイルの不統一 | ファイルごとに書き方が違う | |
| 致命的なミス | 秘密情報のハードコード、データの削除 | |

## ミニ講義（午後）：正しい委ね方の4つの作法（30分）

書籍 4.3〜4.4 の内容を、午前に見つけた問題と対応づけて説明します。

| Vibe Coding の問題 | 4つの作法 | 研修で使う仕組み |
| :--- | :--- | :--- |
| 曖昧な要件による破綻 | 要件定義（プロンプト）の具体化 | Plan モード、要件定義書、設計書 |
| 存在しない検証条件 | 自動テストの積極的な採用 | Vitest、Playwright、TDD |
| スタイルの不統一 | 規約・スタイルの維持 | Biome、CLAUDE.md、npm scripts、CI |
| 致命的なミス | セーフティネットとしてのガードレール | Git、Codespaces、権限設定、ブランチ保護 |

ポイントは、**AI に「気をつけて」とお願いするのではなく、仕組みで強制する**ことです。

## ハンズオン（午後）：Agentic Coding への転換

### 4. ガードレールを設定する

1.  まず現在の状態をコミットします（Git が最初のガードレールです）。

    ```bash
    git add -A && git commit -m "Day2: Vibe Chat change request"
    ```

2.  権限設定のテンプレートを、リポジトリのルートにコピーします。

    ```bash
    mkdir -p .claude && cp hands-on/day2/templates/.claude/settings.json .claude/settings.json
    ```

3.  [settings.json](../hands-on/day2/templates/.claude/settings.json) を開き、`deny`（禁止）、`ask`（毎回確認）、`allow`（自動許可）にそれぞれ何が書かれているかを読みます。
4.  Claude Code のチャットパネルで新しい会話を始めます（設定を読み込み直すため）。

### 5. 危険な操作が止まることを確かめる

ダミーの秘密情報ファイルを作ります。**本物のキーは絶対に使わないでください。**

```bash
echo "API_KEY=dummy-key-for-training-0000" > vibe-chat/.env
```

次の依頼を Claude Code に出し、**拒否される**ことを確認します。

*   「vibe-chat/.env の中身を表示して」
*   「vibe-chat/node_modules を rm -rf で削除して」
*   「git push --force して」

> [!WARNING]
> AI が別の方法（例：`cat` コマンドで読む）で回り込もうとすることがあります。どうなったかを観察し、日報に記録してください。
> 権限設定は万能ではありません。だからこそ、Codespaces による隔離や Git による復元を**重ねて**使います（多層防御）。

続いて、GitHub 上で `main` ブランチに**ブランチ保護**を設定します。

1.  fork したリポジトリの **Settings → Branches**（または **Rules → Rulesets**）を開きます。
2.  `main` に対して、次のルールを設定します。
    *   force push の禁止
    *   削除の禁止
    *   Pull Request 経由でのみマージ可能（Day3 以降に CI 必須も追加）

### 6. Plan モードで不具合を1つ直す

午前に見つけた不具合を1つ選び、今度は **Plan モード**で直します。

1.  チャットパネルのモードを **Plan モード**に切り替えます。
2.  「〇〇が動かない。原因を調査して、修正計画を立てて。修正を確認するテストも計画に含めて」と依頼します。
3.  AI が出した計画を**読んで**、分からないところは質問します。納得したら承認して実行させます。
4.  Vibe Coding で直させたときと比べて、何が違ったかをメモします。

### 7. Vibe Order の要件を読む

明日から作る「Vibe Order」の要求仕様 [vibe-order-requirements.md](../hands-on/day3/prompts/vibe-order-requirements.md) を読みます。

*   AI に渡したときに、解釈が分かれそうな箇所に印を付けます（例：「即時」とは何秒以内か）。
*   チームで共有し、自分なりの答えを要件のメモとして書いておきます。明日、AI から質問されたときに使います。
