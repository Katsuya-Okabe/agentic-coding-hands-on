# 講師ガイド

この研修を運営する講師とサポーター向けのガイドです。

## 研修の設計方針

*   **体験が主役**：座学は各日30分程度に抑え、1日の8割以上を手を動かす時間にします。
*   **失敗させてから解決する**：Day1〜2 では、あえて Vibe Coding のまま進めさせます。途中で正しいやり方を教えたくなっても、Day2 午前までは我慢してください。問題に自分で気づくことが、Day3 以降の学びの動機になります。
*   **数字で比較する**：「なんとなく良くなった」で終わらせないため、比較シートの記入を毎日促します。
*   **書籍との関係**：[AgenticCoding.pdf](ref/AgenticCoding.pdf) の PART3〜7 の流れに沿っています。PART1〜2 はミニ講義の要点のみ、PART7 の AWS デプロイは Codespaces と GitHub Actions に置き換えています。

## 事前準備

### アカウントと契約

*   [ ] 受講者全員に、Claude Code を利用できる**社内契約の Claude アカウント**が割り当てられている
*   [ ] 受講者全員が GitHub アカウントを持ち、研修用の Organization に招待済みである
*   [ ] 1人あたりの AI 利用量の目安と上限を確認している（書籍 PART3 では、Vibe Coding だけで約2.5時間かかっています）

### GitHub

*   [ ] 研修用 Organization で Codespaces が有効で、費用の請求先が設定されている
*   [ ] Codespaces のマシンタイプとして 4コア以上を許可している
*   [ ] アイドルタイムアウトと保持期間を設定している（例：30分、研修終了後7日）
*   [ ] GitHub Actions の利用枠が足りている（1人あたり1日10回程度の CI 実行を想定）
*   [ ] 受講者が fork 先のリポジトリでブランチ保護（Rulesets）を設定できる権限がある
*   [ ] ポート公開範囲で Public を禁止するポリシーを設定している（推奨）

### リハーサル

*   [ ] 講師自身が Day1〜5 を一通り実施し、所要時間と詰まりやすい点を確認している
*   [ ] **講師用のリファレンス実装**（Vibe Order の完成版）を別ブランチに用意している。遅れている受講者の救済に使います
*   [ ] Claude Code 拡張と devcontainer のイメージが、研修当日のバージョンで動くことを確認している

## 日ごとの運営ポイント

### Day1

*   環境構築でつまずく人が必ず出ます。サポーターは午前中、巡回に専念してください。
*   Vibe Coding 中に「コードを読んでもいいですか」と聞かれたら、「今日は読まないでください」と答えます。
*   完成度に差が出ても問題ありません。動かない部分があること自体が、Day2 の材料になります。

### Day2

*   機能追加は60分で打ち切ります。終わらないことも大切な体験です。
*   品質検証は AI に頼らせず、受講者自身にコマンドを実行させます。
*   4分類のワークでは、各チームから1つずつ「一番痛かった問題」を発表させると、午後の講義につながります。
*   ガードレールの体験で、AI が `cat` などで `.env` を読もうとするケースがあります。権限設定だけでは防ぎきれないことを示す好例なので、全体で共有してください。

### Day3

*   Plan モードの計画を、受講者が「読まずに承認」していないかを確認します。計画に対して1つ以上の修正依頼を出すよう促してください。
*   モノレポ構築は環境差で失敗しやすい工程です。14:30 の時点で終わっていない人には、リファレンス実装の雛形を提供して先に進めます。
*   設計工程で AI から質問が来たときに、受講者が答えられずに止まることがあります。Day2 の「曖昧な点のメモ」に立ち返らせてください。

### Day4

*   最も遅れが出やすい日です。frontend は Day5 午前まで延長してよいことを、朝に伝えておきます。
*   AI がテストを書かずに実装を進めていたら、受講者に「テストはどこ？」と AI に聞かせます。
*   会話が長くなると AI の品質が落ちます。パッケージごとに新しい会話を始めているかを確認します。

### Day5

*   変更依頼による比較は、研修の山場です。時間が足りなくなりそうな場合は E2E テストを簡略化し、比較の時間を確保します。
*   発表では、数字の比較だけでなく「自分の役割がどう変わったか」を語らせると、理解が深まります。

## 時間が足りないときの調整

| 状況 | 調整 |
| :--- | :--- |
| Day1 に環境構築が終わらない | ウォーミングアップを省略し、Vibe Chat に直行する |
| Day3 にモノレポ構築が終わらない | リファレンス実装の雛形ブランチを merge させる |
| Day4 に backend が終わらない | frontend をキッチン画面のみに絞る |
| Day5 に E2E が終わらない | E2E は1フロー（注文 → キッチン表示）のみにする |

## よくあるトラブル

| 症状 | 対処 |
| :--- | :--- |
| Claude Code にサインインできない | ブラウザのポップアップブロックを解除する。社内アカウントの割当を確認する |
| Codespaces が重い | マシンタイプを4コア以上に変更する。不要な dev サーバーを止める |
| ポートを開いても画面が出ない | サーバーが `0.0.0.0` で待ち受けているか、PORTS タブで転送されているかを確認する |
| WebSocket がつながらない | フロントエンドの接続先 URL が `localhost` 固定になっていないか確認する（Codespaces では転送先 URL を使う） |
| Playwright が起動しない | `npx playwright install --with-deps chromium` を実行する |
| CI だけ失敗する | CI のログをそのまま AI に貼り付けて原因を調べさせる。`npm ci` と `package-lock.json` の不一致が多い |
| AI が権限設定で拒否された操作を何度も試す | 会話を止め、受講者自身がターミナルで実行するよう指示する |

## 評価

### 評価の観点（ルーブリック）

| 観点 | 3：できている | 2：おおむねできている | 1：要支援 |
| :--- | :--- | :--- | :--- |
| 問題の言語化 | Vibe Coding の問題を4分類で説明し、具体例を挙げられる | 問題を挙げられるが分類があいまい | 問題を説明できない |
| 計画のレビュー | AI の計画に根拠のある修正依頼を出している | 計画を読んでいるが修正依頼は少ない | 計画を読まずに承認している |
| 品質のゲート | テスト、Lint、CI が通る状態を保ち、カバレッジ80%以上 | テストはあるがカバレッジや CI が不十分 | テストや CI がない |
| ガードレール | 権限設定とブランチ保護を設定し、意図を説明できる | 設定はしたが意図の説明が不十分 | 設定していない |
| 振り返り | 比較シートの数字をもとに、自分の役割の変化を説明できる | 比較シートは埋めたが考察が浅い | 比較シートが未記入 |
