AGENTIC CODING HANDS-ON

Agentic Coding
体験研修

Vibe Coding の手軽さから、AIと品質を両立する開発へ

5日間 ／ 新入社員・AI駆動開発入門者向け ／ ベース教材：AgenticCoding.pdf

この研修は、座学ではなく手を動かして Agentic Coding を体験することが目的です。まず Vibe Coding の手軽さを体験し、次にその問題点に直面し、Agentic Coding で解決する、という流れで進みます。

ENVIRONMENT

研修環境

GitHub Codespaces

リポジトリを fork して起動。クラウド上の隔離環境なので、AI が失敗しても PC は無傷

Claude Code

VS Code 拡張のチャットパネルから指示。AI は社内契約の Claude を使う

GitHub Actions

CI で check / test / build / E2E を自動実行。アプリは Codespaces 上でポート公開

書籍の Cline・Amazon Bedrock・AWS 構成は、本研修では上記の環境に読み替えます。

5

DAY 1 ／ PART1〜3

環境構築と Vibe Coding 体験

今日の流れ

  • オリエンテーション、LLM と Agent の要点
  • fork して Codespaces を起動、Claude Code にサインイン
  • 小さな指示で AI の動き方を観察する
  • Vibe Chat を作る（約3時間）
  • チーム内で見せ合い、比較シートに記録

Vibe Coding のルール

  1. 自然言語だけで指示する
  2. AI の提案はそのまま承認する
  3. コードは読まない。画面だけ見て直させる

「読まなかったこと」の代償は、翌日体験します。

6

Vibe Coding 中に「コードを読んでもいいですか」と聞かれたら、今日は読まないでくださいと答えます。完成度に差が出ても問題ありません。動かない部分があること自体が Day2 の材料になります。

DAY 2 ／ PART4

Vibe Coding の限界に直面する

午前：問題を体験し、自分で検証する

  • Vibe Chat に機能追加を依頼（60分で打ち切り）
  • テスト・Lint・npm audit・古いライブラリを自分で調べる
  • 見つけた問題をチームで4つに分類する

曖昧な要件

「イケてる」が人で違う

検証条件がない

壊れても気づけない

スタイル不統一

ファイルごとに書き方が違う

致命的なミス

秘密情報の流出、データ削除

午後：4つの作法を学び、権限設定とブランチ保護でガードレールを張る。Plan モードで不具合を1つ直す。

7

品質検証は AI に頼らず、受講者自身にコマンドを実行させます。ガードレール体験では、AI が cat コマンドなどで .env を読もうと回り込むケースがあります。権限設定だけでは防ぎきれず、多層防御が必要な好例として全体で共有してください。

PART4 ／ 正しい委ね方

お願いではなく、仕組みで強制する

Vibe Coding の問題4つの作法研修で使う仕組み
曖昧な要件要件定義の具体化Plan モード、要件定義書、設計書
検証条件がない自動テストの採用Vitest、Playwright、TDD
スタイル不統一規約・スタイルの維持Biome、CLAUDE.md、npm scripts、CI
致命的なミスガードレールGit、Codespaces、権限設定、ブランチ保護

8

Day2 午後のミニ講義の中心となる表です。午前に受講者が見つけた問題と対応づけて説明します。ポイントは、AI に気をつけてとお願いするのではなく、テストや CI や権限設定で強制することです。

9

Plan モードの計画を受講者が読まずに承認していないかを確認します。計画に対して1つ以上の修正依頼を出すよう促してください。モノレポ構築が14時半の時点で終わっていない人には、リファレンス実装の雛形を提供します。

DAY 5 ／ PART7（読み替え）

同じ変更依頼で Before/After を比較する

比較の観点Before：Vibe ChatAfter：Vibe Order
手戻りの回数Day2 に記録Day5 に記録
壊れた既存機能（デグレ）Day2 に記録Day5 に記録
デグレに気づいたきっかけ手動確認？テスト・CI？
テスト数・カバレッジDay2 に記録Day5 に記録
変更後の安心感（1〜5）Day2 に記録Day5 に記録

比べるのは速さだけではない。壊れたことにすぐ気づけるか、安心して変更できるか。

12　　午前：E2E と CI、Codespaces で公開 ／ 午後：チーム発表と全体振り返り

研修の山場です。時間が足りない場合は E2E テストを1フローに簡略化し、比較の時間を確保します。発表では数字だけでなく「自分の役割がどう変わったか」を語らせると理解が深まります。

EVALUATION

評価の観点

観点「できている」の目安
問題の言語化Vibe Coding の問題を4分類で説明し、具体例を挙げられる
計画のレビューAI の計画に、根拠のある修正依頼を出している
品質のゲートテスト・Lint・CI が通る状態を保ち、カバレッジ80%以上
ガードレール権限設定とブランチ保護を設定し、その意図を説明できる
振り返り比較シートの数字をもとに、自分の役割の変化を説明できる

提出物：自分の fork リポジトリ、比較シート、日報（5日分）、チーム発表資料
